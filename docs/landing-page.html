Keep your backups exactly where they are —
we prove, every day, that they'd actually save you.

Backbeatin is a single-binary Rust tool that automatically tests whether your existing Restic and Borg backups can actually be restored. It runs restore-verify cycles on your schedule, produces tamper-evident signed proofs, and alerts you when a restore would fail — without migrating your backup provider.

Why this exists

I've been running automated backups for years. Every system I've ever managed had some form of backup script cronned into place. And almost none of them had ever been tested.

When you ask someone "when was the last time you actually restored from your backup?" — the answer is almost always "well, not recently" or "we tested it once during setup." That's not a backup strategy; it's a hope.

The standard advice is to periodically do a test restore. But that's manual, slow, and doesn't scale. If you have ten repos across three providers, you're not going to manually restore each one every week. So the backups sit there, accumulating, unverified.

Backbeatin automates the one thing everyone should be doing but nobody does: proving, on a regular cadence, that your restore path still works. It reads your existing repos — it doesn't need you to migrate anywhere — performs a real restore into an ephemeral sandbox, cryptographically verifies the result, signs a tamper-evident proof, and tells you if something broke.

No fabricated statistics. No "trusted by Fortune 500" claims. The only number that matters is whether your latest backup actually restores.

What a proof looks like

Every verification run produces a signed record. A single export bundle contains every run for a repo — including passes and failures. Here's an abbreviated example generated by backbeat demo: 

{
  "version": 1,
  "public_key": "a1b2c3...",  // Ed25519 public key — verify any run signature with this
  "source": "backbeat demo...",
  "runs": [
    {
      "id": 1,
      "snapshot_id": "abc123def",     // The specific snapshot that was restored
      "status": "pass",                // "pass" or "fail"
      "files_count": 42,                // Files restored and verified on disk
      "bytes_restored": 1048576,
      "message": "Restore verified successfully: 42 files...",
      "signature_hex": "f00d...",       // Ed25519 signature over the run data
      "public_key_hex": "a1b2c3..."
    },
    {
      "id": 2,
      "snapshot_id": "456defabc",
      "status": "fail",                 // This run caught a real problem
      "files_count": 0,
      "bytes_restored": 0,
      "message": "restic restore failed (exit 1): ...",
      "signature_hex": "baad..."
    }
  ]
}

The bundle is literal JSON output from the backbeat demo command. Every signature is generated by a real Ed25519 keypair created on first run. The demo spins up a MinIO container, creates a healthy backup (passes), corrupts the repo (fails), and exports both signed results.

Run backbeat demo yourself — it takes about 30 seconds and produces demo-proof-bundle.json in your current directory.

How it works

  1. Point it at your repos Write a TOML config listing your Restic or Borg repositories and the environment variables containing their credentials (never the credentials themselves — they're read from the environment at runtime).
  2. Discovers the latest snapshot backbeat verify runs restic snapshots --json --latest 1 (or borg list --json) locally to find the most recent backup it should test.
  3. Restores into a throwaway Docker container The snapshot is extracted inside an ephemeral container using the official restic/borg Docker image. Credentials are passed as environment variables, never baked into an image. The container is destroyed (force-removed) immediately after verification completes — including the bind-mounted output volume. No restored data survives.
  4. Cryptographically verifies every file Every restored file is hashed with SHA-256 and recorded with its size and relative path. The on-disk file count and structure are compared against the backend's report. A zero-file report from the backend causes a fail (unless the backend doesn't report counts, like Borg).
  5. Signs and stores the result Each run — including the snapshot ID, file count, manifest hash, status, and timestamps — is signed with an Ed25519 keypair (auto-generated in ~/.backbeatin/) and stored in a local SQLite database. The result is exported as a signed JSON bundle.
  6. Alerts on failure In daemon mode, verification runs on each repo's configured cron schedule. On failure, it sends a Slack-formatted webhook to the URL you configure.

Install

Prerequisites: Rust 1.70+, Docker (for sandboxed restore), and the restic or borg CLI binary on your PATH.

cargo install --git https://github.com/eniyos/backbeatin.git or git clone ... && cargo build --release

Or clone and build yourself:

# Clone
git clone https://github.com/eniyos/backbeatin.git
cd backbeatin

# Build
cargo build --release

# Configure (see examples/backbeat.toml)
cp examples/backbeat.toml backbeat.toml
# Edit backbeat.toml with your repo details, then:

# Run a single verification
./target/release/backbeat verify my-repo -c backbeat.toml

# Run the daemon (scheduled verification)
./target/release/backbeat daemon -c backbeat.toml

# Generate a demo proof bundle
./target/release/backbeat demo --output demo-proof-bundle.json

Design constraints

These aren't aspirational — they're enforced in the code:

  • Single static binary. No Python, no Node, no runtime dependencies beyond Docker and the backup CLIs you already have.
  • Never reimplements repository formats. Always shells out to the official restic/borg CLI. It parses their --json output — it doesn't guess at the on-disk format.
  • Read-only by design. Never requires write access to your real backup repository.
  • Ephemeral, isolated restores. Every restore is in a throwaway Docker container destroyed immediately after verification.
  • Self-hosted, no phone-home. No telemetry. No required SaaS. No network calls except to your backup storage, your local Docker socket, and any webhook URL you explicitly configure.
  • Tamper-evident records. Every run is Ed25519-signed at creation time. The proof bundle carries its own public key.
